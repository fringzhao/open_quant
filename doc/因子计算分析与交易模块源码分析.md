# 因子计算、因子分析与交易模拟模块源码分析

## 1. 文档范围

本文分析以下三个文件：

- `src/quant_infra/factor_calc.py`
- `src/quant_infra/factor_analyze.py`
- `src/quant_infra/trade.py`

三个模块共同构成从基础行情到因子生成、因子评价和交易模拟的主要链路：

```text
stock_bar + daily_basic
          │
          ▼
factor_calc.py
  pricing_factors → stock_betas → stock_resids → spec_vol
          │
          ▼
factor_analyze.py
  IC / IR / 分组收益 / 多空收益 / 多轨道 / IC 半衰期
          │
          ▼
trade.py
  选股 → 下期持有 → 交易成本 → 日度组合收益 → 持仓与净值输出
```

## 2. 模块职责概览

| 模块 | 核心职责 | 主要输入 | 主要输出 |
|---|---|---|---|
| `factor_calc.py` | 计算定价因子、股票回归残差和特质波动率 | `stock_bar`、`daily_basic` | `pricing_factors`、`stock_betas`、`stock_resids`、`spec_vol` |
| `factor_analyze.py` | 评价因子的预测能力、分组表现和稳健性 | 任意因子表、`stock_bar`、指数行情及成分股 | 评价结果表、CSV、净值图、IC 图、半衰期图 |
| `trade.py` | 模拟小资金按因子选股交易 | 因子表、`stock_bar`、`stock_basic`、指数行情 | 持仓 CSV、交易收益表、净值图 |

## 3. 共同依赖与数据约定

### 3.1 核心数据库表

| 表 | 使用模块 | 必要字段 |
|---|---|---|
| `stock_bar` | 三个模块 | `ts_code`、`trade_date`、`pct_chg`；交易模拟还使用 `close` |
| `daily_basic` | `factor_calc.py` | `ts_code`、`trade_date`、`total_mv`、`pb` |
| `stock_basic` | `trade.py` | `ts_code`、`name` |
| `index_data` | `factor_analyze.py`、`trade.py` | `ts_code`、`trade_date`、`pct_chg` |
| 用户因子表 | `factor_analyze.py`、`trade.py` | `ts_code`、`trade_date`、默认字段 `factor` |

### 3.2 日期和收益口径

- 数据库日期主要使用 `YYYYMMDD` 字符串或整数。
- 股票和指数的 `pct_chg` 以百分数保存，例如 `2.5` 表示上涨 2.5%。
- 分析和交易模块会将其除以 100，转换成小数收益 `0.025`。
- 年化交易日数固定使用 242。
- 周期映射来自 `FREQ_MAP`，目前包括日度、周度和月度。

### 3.3 当前数据源依赖

三个文件尚未全部切换到 AKShare 版本：

- `factor_calc.py` 使用 `from quant_infra import db_utils, get_data`。
- `factor_analyze.py` 使用 `from quant_infra.get_data import get_ins, get_index_data`。
- `trade.py` 使用 `from quant_infra.get_data import get_ins, get_index_data`。

因此，即使 `get_data_ak.py` 已完成迁移，这三个模块仍可能触发旧 Tushare 逻辑。后续应统一改为 `get_data_ak`，并进行回归测试。

## 4. `factor_calc.py` 源码分析

## 4.1 模块目标

该模块实现一条逐级依赖的因子生产链：

```text
股票收益 + 每日估值
        │
        ▼
MKT / SMB / HML / UMD
        │
        ▼
股票多因子 Beta
        │
        ▼
股票日度残差
        │
        ▼
20 日残差标准差（特质波动率）
```

### 4.2 `calc_single_pricing_factors()`

作用：计算单个交易日的四个定价因子。

计算口径：

- `MKT`：当日所有有效股票 `pct_chg` 的算术平均值。
- `SMB`：按上月市值排序，低市值组三分之一收益减高市值组三分之一收益。
- `HML`：按上月 PB 排序，低 PB 组三分之一收益减高 PB 组三分之一收益。
- `UMD`：按上月收益排序，高收益组三分之一收益减低收益组三分之一收益。

有效性限制：

- 当日有效股票少于 9 只时返回 `None`。
- 单个排序指标至少需要 3 个有效样本。
- 返回的因子单位仍是百分数，与 `stock_bar.pct_chg` 相同。

### 4.3 `compute_pricing_factors()`

处理流程：

1. 调用 `get_data.get_dates_todo('pricing_factors')` 获取待计算日期。
2. 向前读取上一个月的完整数据，为滞后一期指标提供基础。
3. 将 `stock_bar` 与 `daily_basic` 按股票和日期内连接。
4. 按股票和月份聚合月收益、市值和 PB。
5. 对月度结果执行 `shift(1)`，生成上月收益、上月市值和上月 PB。
6. 将滞后指标合并回日度数据。
7. 按交易日并行调用 `calc_single_pricing_factors()`。
8. 追加写入 `pricing_factors`。

输出字段：

```text
trade_date, MKT, SMB, HML, UMD
```

值得注意的口径问题：

- 注释称 SMB 使用“流通市值”，实际 SQL 使用 `daily_basic.total_mv`，即总市值。
- 月收益使用 `pct_chg.sum()`，而不是复利收益 `(1 + ret).prod() - 1`。短周期差异可能有限，但严格意义上不是月度累计收益。
- HML 使用低 PB 减高 PB，是价值减成长的近似实现，但并非标准账面市值比构造。

### 4.4 `calc_single_beta()`

使用最小二乘法估计：

```text
股票收益 = 截距 + βMKT·MKT + βSMB·SMB + βHML·HML + βUMD·UMD + 残差
```

要求单只股票至少有 220 个有效交易日，输出：

```text
ts_code, intercept, MKT_beta, SMB_beta, HML_beta, UMD_beta, update_date
```

### 4.5 `calc_single_resid()` 与 `calc_resid()`

`calc_single_resid()` 根据已估计 Beta 计算每日预测收益和残差：

```text
resid = 实际 pct_chg - 模型预测 pct_chg
```

`calc_resid()` 的整体流程：

1. 先调用 `compute_pricing_factors()`。
2. 获取 `stock_resids` 的待更新日期。
3. 检查 `stock_betas` 是否存在超过 5000 条记录。
4. 若 Beta 不足，按股票并行估计 Beta 并覆盖 `stock_betas`。
5. 将股票收益、定价因子和 Beta 合并。
6. 按股票并行计算残差。
7. 将结果追加到 `stock_resids`。

### 4.6 `calc_spec_vol()`

作用：计算 20 个交易日滚动残差标准差：

```text
factor(t) = std(resid[t-19:t])
```

为了满足窗口长度，函数会从首个待更新日期向前多读取 45 个自然日。只有至少 20 个有效残差时才输出，结果写入：

```text
spec_vol(ts_code, trade_date, factor)
```

### 4.7 `winsorize()`

使用全序列均值和标准差，将数据裁剪到：

```text
[mean - n×std, mean + n×std]
```

这是标准差缩尾，而非按分位数缩尾。该函数随后被因子评价和交易模块复用。

### 4.8 `factor_calc.py` 的主要风险

1. **Beta 样本范围可能不符合注释。** `calc_resid()` 查询的股票收益只覆盖本次待更新区间；首次缺少 Beta 时，也在这个区间上估计 Beta。若增量区间不足 220 日，将无法生成 Beta，而不是使用“全历史数据”。
2. **Beta 是否存在的判断较脆弱。** 代码以记录数是否大于 5000 判断，没有检查股票覆盖率、更新时间或数据版本。
3. **Beta 不会定期更新。** 一旦记录数超过阈值，模型参数可能长期保持不变。
4. **增量写入缺少数据库唯一约束。** `pricing_factors`、`stock_resids`、`spec_vol` 都采用追加写入，异常重跑可能产生重复数据。
5. **月收益使用简单求和。** 建议统一改为复利累计。
6. **并行度固定为 `n_jobs=-1`。** 大数据量时可能产生较高内存和 CPU 压力。
7. **异常处理偏宽。** 多处仅打印错误并跳过，可能得到不完整但表面成功的结果。

## 5. `factor_analyze.py` 源码分析

## 5.1 模块目标

该模块负责回答以下问题：

- 因子值能否预测下一期收益？
- 因子分组是否呈现单调性？
- 最高组相对最低组是否有稳定超额收益？
- 结果对调仓日期是否敏感？
- 因子的 IC 能维持多少个交易日？

### 5.2 `calc_ic()`

计算每日或每周期横截面 Rank IC：

1. 将因子和下一期收益分别透视为“日期 × 股票”的宽表。
2. 过滤有效股票数不超过 `MIN_IC_SIZE` 的日期。
3. 对每个横截面做百分比排名。
4. 对排名后的因子和收益计算 Pearson 相关，即 Spearman Rank IC。

输出：

```text
trade_date, ic
```

该实现向量化程度较高，但 `pivot()` 要求同一股票同一日期只有一条记录；因子表或行情表有重复键时会直接报错。

### 5.3 `specific_group()`

这是因子评价的核心函数，单次处理一个“样本 × 调仓频率 × 轨道偏移”组合。

主要步骤：

1. 根据轨道延迟映射调整名义日期。
2. 将日期转换为日、周或月周期。
3. 非日频时：
   - 股票收益按周期复利聚合；
   - 因子取周期最后一个值；
   - 股票收益 `shift(-1)` 得到下一期收益。
4. 日频时直接使用原始收益，并按股票 `shift(-1)`。
5. 合并当期因子和下一期收益，计算 IC 与 IR。
6. 按每期因子百分位划分 `n_groups` 个组。
7. 将当期分组映射到下一持有周期。
8. 使用日度股票收益计算各组等权收益。
9. 生成最高组、最低组和多空组合日收益。
10. 计算 IC、IR、多空夏普、Top/Bottom Sortino 和各组年化收益。

返回字典包含摘要指标，以及两个嵌套 DataFrame：

- `daily_ls`：多头、空头、多空和基准的日度收益。
- `ic_series`：各期 IC 序列。

### 5.4 `prepare_evaluate_data()`

该函数统一准备评价数据：

- 从指定因子表读取因子值。
- 从 `stock_bar` 读取股票收益并做标准差缩尾。
- 根据 `samples` 选择全市场或指数样本。
- 根据因子频率生成允许的评价频率组合。
- 从 CSV 或数据接口读取指数成分股。
- 获取基准指数收益。
- 返回样本级因子、行情、组合列表和交易日序列。

返回值：

```text
(sample_fac, sample_stk, bench_df, combinations, trade_days)
```

### 5.5 `evaluate_factor()`

标准因子评价入口：

1. 调用 `prepare_evaluate_data()`。
2. 对所有“样本 × 频率”组合并行执行 `specific_group()`。
3. 将日度多空收益写入 `{factor_table}_daily_ls`。
4. 将 IC 序列写入 `{factor_table}_ic_series`。
5. 将摘要指标输出到 `factor_mining/{factor_table}/output/summary.csv`。

### 5.6 `evaluate_factor_pathways()`

多轨道评价通过对调仓边界施加 0 到 `n_pathways-1` 个交易日的偏移，观察同一因子在不同建仓日期下的表现。

输出：

- `{factor_table}_pathway_daily_ls`
- `{factor_table}_pathway_ic_series`
- `pathway_summary.csv`
- 多轨道累计超额收益图

该功能主要用于识别因子是否只在某个特定调仓日有效。

### 5.7 绘图函数

#### `group_plot()`

支持三种数据来源：

- `evaluate`：标准分组评价结果。
- `trade`：交易模拟结果。
- `pathway`：指定轨道结果。

绘制策略净值、基准净值和相对净值，并计算：

- 超额年化收益
- 年化波动率
- 最大回撤
- Calmar 比率

#### `pathway_plot()`

比较多轨道最终累计超额收益，绘制最优、平均和最差轨道，并显示轨道编号。

#### `ic_plot()`

绘制 IC 柱状图和累计 IC 曲线。

### 5.8 `cal_single_lag()` 与 `ic_half_life()`

`ic_half_life()` 将未来收益分别向前移动 1 至 `max_lag` 个交易日，计算每个滞后期的平均 Rank IC。

半衰期定义为：

```text
首次满足 |IC(lag)| ≤ |IC(lag=1)| / 2 的 lag
```

输出图片：

```text
factor_mining/{factor_table}/output/ic_half_life.png
```

### 5.9 `factor_analyze.py` 的主要风险

1. **日频持有期使用自然日偏移。** `hold_period = period + 1` 对日频 `Period('D')` 增加的是一个自然日。周五的分组会映射到周六，而不是下一个交易日，可能丢失周一持有收益。这是优先级较高的逻辑问题。
2. **当前指数成分股会带来生存者偏差。** 回测历史区间使用当前成分股 CSV，而非历史时点成分股。
3. **动态 SQL 未校验标识符。** `factor_table`、`other_name`、`line` 等直接拼入 SQL，错误输入可能导致 SQL 异常，也存在注入风险。
4. **空结果保护不足。** `results`、`daily_ls_list` 或 `ic_series_list` 为空时直接 `pd.concat()` 会报错。
5. **透视表对重复键敏感。** 因子表重复的 `ts_code + trade_date` 会使 `pivot()` 失败。
6. **轨道日期映射逻辑较难验证。** 起始缺失位置统一填充首个交易日，可能使开头多天映射到同一日期。
7. **绘图异常被吞掉。** 绘图函数捕获所有异常并打印，调用方无法判断是否成功生成文件。
8. **字体配置依赖 Windows 字体。** `Microsoft YaHei` 在 macOS/Linux 上可能不存在。
9. **`ic_half_life()` 文档与返回值不一致。** 文档声明返回 DataFrame，实际最终 `return` 为 `None`。
10. **年化公式缺少空数据和异常净值保护。** 数据为空、净值为负或长度为零时可能报错或产生无效值。

## 6. `trade.py` 源码分析

## 6.1 模块目标

该模块在因子分组评价之外，模拟更接近小资金实际操作的 Top-N 选股：

- 限制股价。
- 排除无权限交易的板块。
- 选择每期因子排名靠前的股票。
- 加入手续费和滑点。
- 输出具体持仓及日度收益。

### 6.2 `simulate_trade()`

主要参数：

| 参数 | 含义 |
|---|---|
| `factor_table` | 因子表名 |
| `trade_freq` | 日度、周度或月度调仓 |
| `bench_index` | 基准指数代码 |
| `sample` | 全市场或指定指数样本 |
| `n_top` | 每期持仓股票数量 |
| `is_ascending` | 因子排序方向 |
| `commission_rate` | 单边手续费，输入单位为万分比 |
| `slippage_rate` | 单边滑点，输入单位为百分比 |
| `price_max` | 股票价格上限 |
| `filter_boards` | 排除创业板、科创板或北交所 |

执行流程：

1. 将手续费和滑点转换成小数。
2. 将因子表与 `stock_bar` 连接，过滤高价股。
3. 读取股票日收益并做三倍标准差缩尾。
4. 读取 `stock_basic` 建立股票名称映射。
5. 按股票代码前缀排除指定板块。
6. 获取基准指数收益。
7. 根据指数成分股限制样本范围。
8. 每个周期取最后一个因子值并排序。
9. 将选出的 Top-N 股票安排到下一周期持有。
10. 输出 `trade_holdings.csv`。
11. 调用 `compute_portfolio_daily_ret()` 计算含成本日收益。
12. 计算多头年化夏普。
13. 写入 `{factor_table}_trade_daily_ret` 并调用 `group_plot()` 绘图。

### 6.3 `compute_portfolio_daily_ret()`

该函数对每个持有周期独立计算：

1. 从 `holdings` 取得当前和上一期持仓。
2. 使用集合差计算卖出和买入比例。
3. 首次建仓扣一次买入成本。
4. 后续按卖出比例和买入比例分别扣单边成本。
5. 对当期持仓股票按日做等权平均。
6. 在每期第一个交易日一次性扣除换仓成本。
7. 并行合并所有持有周期结果。

成本公式：

```text
one_way_cost = slippage_rate + commission_rate

cost = (
    卖出股票数 / 上期股票数
    + 买入股票数 / 本期股票数
) × one_way_cost
```

### 6.4 主要输出

#### 持仓文件

```text
factor_mining/{factor_table}/output/trade_holdings.csv
```

包含样本、换仓日、持有周期、股票代码、股票名称和持仓数量。

#### 数据库结果

```text
{factor_table}_trade_daily_ret
```

核心字段包括：

```text
trade_date, long, bench_ret, 样本, 频率
```

### 6.5 `trade.py` 的主要风险

1. **日频调仓存在自然日偏移问题。** 与 `specific_group()` 相同，`period + 1` 不是“下一个交易日”。
2. **只模拟收益，没有成交可行性约束。** 未处理停牌、涨跌停、成交量不足、无法买入或卖出等情况。
3. **缺失股票收益会被自动重新等权。** 某只持仓股票当日缺少行情时，组合会只对剩余股票平均，可能高估可实现性。
4. **换仓成本简化。** 成本在持有期第一天一次扣除，没有使用实际成交价、开盘价、买卖价差或最低佣金。
5. **当前指数成分股带来生存者偏差。** 历史回测没有按历史日期恢复成分股。
6. **股票代码前缀规则不完整。** 北交所过滤只包含 `4` 和 `8`，未覆盖可能以 `9` 开头的代码。
7. **动态 SQL 风险。** 因子表名和字段名直接拼入 SQL。
8. **选股方向容易误用。** `is_ascending=False` 实际为降序并选择因子值最高的股票，调用方需要特别注意。
9. **结果表使用覆盖写入。** 同一因子只能保留最后一次交易模拟参数的结果，参数没有全部写入表中。

## 7. 三个模块的调用关系

```text
factor_calc.py
  compute_pricing_factors
      └─ get_data.get_dates_todo
  calc_resid
      ├─ compute_pricing_factors
      ├─ calc_single_beta
      └─ calc_single_resid
  calc_spec_vol
      └─ stock_resids

factor_analyze.py
  evaluate_factor
      ├─ prepare_evaluate_data
      │   ├─ get_ins
      │   └─ get_index_data
      └─ specific_group
          └─ calc_ic
  evaluate_factor_pathways
      ├─ prepare_evaluate_data
      ├─ specific_group
      └─ pathway_plot
  group_plot / ic_plot / ic_half_life

trade.py
  simulate_trade
      ├─ get_ins
      ├─ get_index_data
      ├─ winsorize
      ├─ compute_portfolio_daily_ret
      └─ group_plot
```

## 8. 建议的运行顺序

```text
1. 更新 stock_bar、daily_basic、stock_basic、index_data 和指数成分股
2. compute_pricing_factors()
3. calc_resid()
4. calc_spec_vol()
5. evaluate_factor() 或 evaluate_factor_pathways()
6. group_plot()、ic_plot()、ic_half_life()
7. simulate_trade()
```

其中 `calc_resid()` 内部会调用 `compute_pricing_factors()`，但在正式任务中仍建议明确检查每层数据是否完整。

## 9. 优先改进建议

### P0：影响正确性

1. 将三个模块的数据接口统一切换到 `get_data_ak`。
2. 修复日频调仓使用自然日 `Period + 1` 的问题，改为显式的下一交易日映射。
3. 修复首次 Beta 计算只读取增量区间的问题，Beta 应使用足够长的历史窗口。
4. 为关键结果表建立 `ts_code + trade_date` 或 `trade_date` 唯一性保障，实现幂等写入。

### P1：降低偏差

1. 使用历史指数成分股，减少生存者偏差。
2. 将月收益从简单求和改为复利累计。
3. 明确定价因子使用总市值还是流通市值，并统一文档和代码。
4. 在交易模拟中处理停牌、涨跌停和缺失行情。
5. 为 Beta 增加滚动更新或定期重估机制。

### P2：工程质量

1. 对动态表名、列名和样本参数做白名单校验。
2. 为所有 `pd.concat()` 增加空列表保护。
3. 将 `n_jobs`、窗口长度、年化交易日数等改为配置项。
4. 统一异常处理，区分“无数据”“数据不完整”和“执行失败”。
5. 将测试代码与生产模块分离，并补充关键数学逻辑的单元测试。
6. 使用跨平台中文字体回退配置。

## 10. 总结

三个模块的总体分层清晰：`factor_calc.py` 负责生成因子，`factor_analyze.py` 负责研究评价，`trade.py` 负责加入现实约束后的选股交易模拟。代码已经包含增量计算、并行计算、多频率评价、多轨道分析、IC 半衰期和交易成本等较完整的量化研究能力。

当前最重要的问题不是缺少功能，而是少数细节会直接影响回测正确性和可复现性，特别是旧 Tushare 导入、日频自然日偏移、Beta 历史窗口以及追加写入重复风险。优先修复这些问题后，整个研究链路的可靠性会明显提升。
